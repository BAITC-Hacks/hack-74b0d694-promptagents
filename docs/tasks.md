# Три независимых задания после каркаса

Каждый начинает от одного коммита каркаса в своей сессии и ветке. Не создавайте
ветки до получения этого общего коммита. Контракт v1.0.0 согласован в
`docs/api-contract.md`; примеры из `docs/examples/` — только для разработки UI.
Общие изменения согласует №1; не редактируйте файлы другого владельца.

## №1 — подбор, загрузка признаков, интеграция

Ветка: `codex/backend-matching`. Владение: `backend/app/` кроме explanations.py,
контракт, общие конфиги, зависимости backend, README, интеграция веток.

1. Использовать исходный CSV в корне; импорт и ожидаемые характеристики уже
   проверены. Не править оригинал и не конвертировать его ради запуска.
2. Реализовать чистую функцию подбора с фиксированными фильтрами, нормализацией,
   тремя исходами, top-3, формулой и диагностикой по контракту.
3. Реализовать загрузку/проверку prepared-артефакта, baseline при отсутствии или
   устаревании. Сохранить origin, evidence и предупреждения. Структурированные
   поля важнее description/AI; противоречивая цитата не является доказательством.
4. Подключить explain() №3 по существующей сигнатуре. До интеграции использовать
   внедряемую тестовую функцию в своих локальных проверках, не выдавать её за продукт.
5. Подключить функцию к POST, выставить recommendation_implemented=true только
   после интеграции. Сохранить 422/503, завершить пользовательские сообщения.
6. Интегрировать №2 и №3, выполнить тесты и сборку, обновить README по фактам.

Готово: все условия соблюдены без AI-ключа; нет двойного подсчёта исключений;
baseline/prepared честно обозначены; повторный запрос стабилен; ошибки данных
не похожи на no_match. Выполнен полный чек-лист ниже, доступен реальный демозапуск.

## №2 — форма, карточки, диагностика

Ветка: `codex/frontend`. Владение: только `frontend/`.

1. Доработать готовую форму/клиент API и шесть демокнопок по types и контракту. Учесть загрузку,
   повторный запрос, ошибки 422/503/501, отмену/защиту от устаревших ответов.
2. Реализовать три различимых бизнес-исхода, до трёх карточек, число подходящих,
   объяснения и доступный просмотр evidence. Цена — «от», все флаги/origin —
   понятными метками, baseline/prepared — достоверно.
3. Отображать причины исключения и недостаточного числа карточек. Сравнивать
   смену даты только при остальных одинаковых условиях и data_version;
   заявления о занятости подтверждать busy_profiles нового ответа.
   Сохранять глобальный список категорий, чтобы можно было выбрать отсутствующую
   в городе категорию. Демокнопки подставляют параметры и вызывают API, не готовый ответ.
4. Пока backend не завершён, разрабатывать на отдельном явном fixture/mock-режиме
   по docs/examples; по умолчанию всегда обращаться к API. Пометка «Тестовые данные»
   обязательна в fixture-режиме. Не подключать фикстуры к реальному каталогу.
5. Убрать баннер каркаса после интеграции готового recommend. Проверить мобильную
   ширину, подписи полей, клавиатуру, loading/error/empty/success.

Готово: npm ci и npm run build проходят; все три исхода и инфраструктурные ошибки
различимы; нет рекламных выдумок, обещаний конечной цены и скрытого mock-режима.

## №3 — объяснения, AI-подготовка, тесты и демо

Ветка: `codex/explanations-tests`. Владение: `backend/app/explanations.py`,
`scripts/`, `tests/`, `data/derived/`, `docs/demo.md`.

1. Реализовать explain() без изменения сигнатуры: детерминированный baseline,
   проверяемые поля/цитаты, 1–2 предложения; поддержка валидных prepared features.
2. Создать отдельный необязательный CLI-экстрактор AI-признаков. Зафиксировать
   промпт, версию модели, SHA-256 исходника/промпта. Подтверждать каждый признак
   точной цитатой и её смыслом. Невалидное не сохранять. Новые зависимости
   согласовать с №1. Никакой сети внутри explain() или recommend.
3. Расширить тесты по чек-листу; до готовности движка №1 писать тесты HTTP-контракта
   и объяснений отдельно, будущие проверки recommend помечать явно ожидающими
   реализации. Перед финалом убрать эти пропуски и выполнить проверки вместе.
4. Шесть реальных сценариев CSV уже проверены в scripts/check_demos.py и тестах.
   После готовности №1 продублировать проверки ожидаемых множеств ID через
   настоящий API, дополнить проверками объяснений и UI. Запросы, SHA-256 и
   доказательства — docs/demo.md. Тестовые каталоги — только tests/fixtures/.

Готово: baseline работает без ключа и derived; объяснения подтверждены;
AI-артефакт воспроизводимо загружается, а несовместимый не используется;
демо проверено на реальном каталоге, тесты проходят после интеграции.

## Общий чек-лист приёмки (ещё не выполнен для recommend)

- Занятый профиль никогда не выдан; смена только даты меняет выдачу в найденном
  реальном сценарии, busy_profiles содержит подтверждающий календарь.
- Повторный запрос даёт тот же порядок; равная цена разрешается строковым id;
  подтверждённая специализация выше цены, без признаков все баллы равны нулю.
- category_absent отличается от no_match и от ошибок 422/503.
- Отдельно проверены город, категория, бюджет, формат, язык, длительность,
  нормализация, отсутствие необязательных полей.
- max_hours=null не исключает; равенство цены/длительности границе разрешено.
- Возвращается максимум 3; 1–2 имеют объяснение дефицита, >3 — общее число.
- Сумма исключённых + eligible_count = total_candidates, никакого двойного счёта.
- Каждое утверждение и цитата подтверждены; цена «от» не обещает итоговую стоимость.
- Флаги и origin различимы; исходные и командные синтетические записи не смешаны.
- Без AI-ключа/артефакта — baseline; устаревший хеш/схема/промпт, неверный id или
  неподтверждённая цитата не влияют на рекомендации.
- Вне окна дат, неверная дата, неположительное число — 422; плохой/пустой CSV,
  повтор id, неверные типы/значения — 503 с диагностикой.
- Ответ на реальном каталоге укладывается в ориентир 10 секунд; npm build,
  pytest и ручная проверка пользовательского сценария выполнены.

Рекомендуемый бюджет оставшегося времени: 60% — независимая реализация,
25% — интеграция владельцем №1, 15% — реальное демо и исправления.
