# API и архитектура v1.0.0

React → Vite proxy `/api` → FastAPI → CSV в памяти. `catalog.py` проверяет
данные при старте; `models.py` — источник схем, `frontend/src/contracts.ts` —
TypeScript-зеркало. OpenAPI: `/openapi.json`, интерактивная документация: `/docs`.
Перезагрузка данных — перезапуск backend. БД и обязательных внешних API нет.

Будущий pipeline: город + категория → жёсткие фильтры → ранжирование → до 3
профилей → `explain()` → карточки и диагностика. Сейчас работают загрузчик,
health, options и валидация входа; recommend возвращает 501 при готовом каталоге.

## Запрос

`POST /api/recommend`, `Content-Type: application/json`:

```json
{
  "city": "Алматы",
  "date": "2026-10-10",
  "event_format": "свадьба",
  "category": "Ведущий",
  "budget_kzt": 300000,
  "duration_hours": 4,
  "language": "русский"
}
```

Это пример формы запроса; проверенные демосценарии — в `docs/demo.md`. Все поля, кроме
`duration_hours` и `language`, обязательны. Необязательные поля можно опустить
или передать `null`. Числа — конечные JSON numbers > 0 (не строки и не boolean),
дробные значения разрешены. Пустая строка языка ошибочна. Лишние поля запрещены.

Дата — строго `YYYY-MM-DD`, существующая дата включительно от 2026-09-23 до
2026-12-31. Вне окна — 422: отсутствие дат занятости не доказывает доступность.
Строки города/категории/формата/языка: Unicode NFC, обрезка и схлопывание
пробелов, `casefold()`. Сравнение только по равенству такого ключа; без
транслитерации, синонимов и замены города. Исходные подписи каталога сохраняются.
Неизвестный непустой город или категория допустимы и ведут к `category_absent`;
неизвестный формат/язык проверяется фильтром и может дать `no_match`.

## Методы и ошибки

| Метод | Результат |
| --- | --- |
| `GET /api/health` | 200: `status`, `contract_version`, `dataset_status`, `profile_count`, `data_version`, `recommendation_implemented`, `issues` |
| `GET /api/options` | 200: `cities`, `categories`, `event_formats`, `languages`, `categories_by_city`, `date_range: {min,max}`, `data_version`; 503 при ошибке данных |
| `POST /api/recommend` | Будущий 200 по схеме ниже; сейчас 501, если данные готовы, иначе 503; неверный вход всегда 422 |

Health — проверка процесса и каталога, не заявление о готовности подбора.
`status=degraded`, `dataset_status=missing|invalid`, `data_version=null`,
`profile_count=0` при ошибке данных; подробности в `issues`. При валидном каталоге
`status=ok`, `dataset_status=ready`; `recommendation_implemented=false` до интеграции.

Options берёт только реально присутствующие значения. Массивы сортируются по
нормализованной строке, для равенства — по исходной Unicode-строке. Для одинаковых
нормализованных значений выбирается минимальная исходная строка. `categories` —
общий список; `categories_by_city` — подсказки, а не запрет отправить редкую пару.

Ошибки 422/503/501 имеют единую форму:

```json
{"error":{"code":"not_implemented","message":"Подбор ещё не реализован. Это каркас приложения.","issues":[]}}
```

Коды: `validation_error` (422), `dataset_missing` / `dataset_invalid` (503),
`not_implemented` (501). Issue: `{line: number|null, id: string|null,
field: string|null, message: string}`. Синтаксическая ошибка JSON тоже 422.
Ошибки никогда не превращаются в бизнес-исход `no_match`.

## Успешный ответ recommend (согласован, пока не реализован)

| Поле | Значение |
| --- | --- |
| `status` | `matched` / `category_absent` / `no_match` |
| `message` | Понятное объяснение исхода и количества; при 1–2 объяснить дефицит, при >3 указать общее число |
| `normalized_request` | Вход после нормализации; необязательные поля явно `null`, если не заданы |
| `total_candidates` | Число профилей с городом и категорией до остальных фильтров |
| `eligible_count` | Число прошедших все условия до ограничения top-3 |
| `cards` | От 0 до 3 карточек |
| `diagnostics` | `filters`, `busy_profiles`, `warnings` |
| `explanation_mode` | `baseline` или `prepared` |
| `data_version` | `sha256:<64 hex>` от точных байтов исходного CSV |

`category_absent`: total=eligible=0, cards=[]; `no_match`: total>0, eligible=0,
cards=[]; `matched`: eligible>0, длина cards=min(3,eligible).
Статус ответа HTTP 200 для всех трёх бизнес-исходов.

Карточка: `id`, `name` (=anon_name), `category` (выбранная категория), `city`,
`price_from_kzt`, `explanation` (1–2 предложения), `evidence` (непустой список),
`synthetic`, `city_imputed`, `price_imputed`, `origin`.
`origin`: `source_original` — исходная анонимизированная запись;
`source_synthetic` — синтетическая запись организаторов;
`team_synthetic` — отдельная добавленная командой запись. Для исходного файла
origin вычисляется по `synthetic`, а не по имени/id. Если команда позже добавит
свои записи, нужен отдельный файл и явные метаданные происхождения; нельзя
смешивать их с исходным каталогом или менять его молча. Сейчас добавлений нет.

Метки UI: «Синтетический профиль», «Город указан при подготовке данных»,
«Цена указана при подготовке данных» при соответствующих true. Происхождение
показывать отдельно: «Исходный каталог», «Синтетика организаторов», «Добавлен командой».
Цена всегда «от … ₸»; совпадение стартовой цены не гарантирует итоговый бюджет.

## Фильтры, диагностика и порядок

После отбора города и категории порядок фильтров фиксирован:

1. `busy`: запрошенная дата входит в `busy_dates` → исключить.
2. `budget`: `price_from_kzt > budget_kzt` → исключить.
3. `format`: формат отсутствует в `event_formats` → исключить.
4. `language`: язык задан и отсутствует в `languages` → исключить.
5. `duration`: длительность задана, `max_hours != null` и превышена → исключить.

Равенство цены и длительности границе допустимо. `max_hours=null` не исключает
кандидата и не означает «работает неограниченно долго» — присутствие не применимо.
Нет автоматического расширения города, бюджета, даты или иных условий.

`diagnostics.filters` всегда пять объектов в этом порядке:
`{reason, excluded_count, remaining_count}`. Считаются только впервые исключённые
на этапе профили; сумма excluded_count + eligible_count = total_candidates.
Пропущенный необязательный фильтр имеет excluded_count=0. Для category_absent —
пять нулевых этапов. При 1–2 результатах отличать маленький исходный каталог
от исключений условиями, опираясь на эти числа.

`busy_profiles`: только профили выбранных города и категории, исключённые первым
этапом, в порядке id. Объект `{id,name,date,evidence}`; evidence.field=`busy_dates`,
value содержит исходный список дат, в котором обязательно есть date.
Frontend сравнивает два ответа только при одинаковых параметрах кроме date и
одинаковом data_version. Исчезновение само по себе не доказывает занятость:
сообщение «X занят» разрешено только при наличии X в busy_profiles нового ответа.
Иначе причина может быть сдвигом top-3. Это запланированная функция, не готовый UI.

Формула ранжирования (инженер №1):
`(-specialization, price_from_kzt, id)` по возрастанию; specialization ∈ {0,1}.
Значение 1 только при валидном `format_specialization` для выбранного формата с
подтверждающей точной цитатой из description. Просто членство в event_formats
не добавляет балл. При отсутствии/устаревании признаков — 0 у всех.
Структурированные поля имеют приоритет над description и AI. Они не могут
расширять event_formats/languages/max_hours или менять календарь/цену. Если текст
им противоречит, противоречивая часть не может стать evidence соответствия.

id — исходная уникальная строка; сравнение Python Unicode code point, чувствительно
к регистру, без numeric/natural sort, locale или нормализации. Например, `HK-10`
предшествует `HK-2`. Версия формулы: `specialization-price-id-v1`.
Детерминизм гарантируется при одинаковых данных, артефакте признаков и конфигурации.

## Объяснения и подготовленные признаки

Интерфейс №3: `explain(profile: Profile, request: RecommendRequest,
features: tuple[PreparedFeature, ...] = ()) -> Explanation` в `explanations.py`.
Возвращает `{text,evidence,mode}`. Функция сейчас явно поднимает NotImplementedError.
Вызывается после фильтрации; не меняет порядок, не обращается к сети. Инженер №1
передаёт только валидные признаки. Пустые features требуют работоспособного baseline.

Evidence: `{source: profile|description|prepared, field, value, quote: string|null}`.
Для profile — точное имя поля и исходное значение. Для description/prepared —
field=`description`, value=исходное описание, quote=непустая точная подстрока
описания. Подготовленный признак не является самостоятельным доказательством.
Релевантность специализации проверяется отдельно от вхождения цитаты: цитата
должна явно подтверждать формат, а не просто встречаться в описании.

Baseline: конкретные факты о параметрах заказа + релевантная отличительная цитата,
если есть; без выдумывания достоинств. Если отличительного факта нет, честное
объяснение по полям. Не выдавать baseline за вызов LLM. `explanation_mode=prepared`
только если хотя бы одна выданная карточка использует проверенный AI-признак;
иначе baseline. Для пустой выдачи — baseline.

Планируемый `data/derived/features.json`:

```json
{
  "schema_version": "1.0.0",
  "dataset_sha256": "<SHA-256 точных байтов CSV, 64 hex>",
  "model": "<провайдер/точная версия модели>",
  "prompt_version": "features-v1",
  "prompt_sha256": "<SHA-256 текста промпта, 64 hex>",
  "generated_at": "<ISO-8601 UTC>",
  "profiles": {
    "<исходный id>": [{
      "kind": "format_specialization",
      "event_format": "свадьба",
      "value": "свадьба",
      "quote": "<точная цитата, явно подтверждающая специализацию>"
    }]
  }
}
```

Это схема с плейсхолдерами, не реальные подготовленные данные. Второй kind —
`distinctive_detail`: value — краткое свойство, event_format — формат, для которого
оно релевантно; quote обязателен в обоих случаях. Без доказательства — не сохранять.
Экстрактор №3 работает один раз отдельной CLI-командой и сохраняет артефакт;
провайдер будет выбран №3. До этого внешней AI-интеграции нет.

№1 проверяет схему, dataset_sha256, поддерживаемый prompt_version=`features-v1`,
наличие id, совпадение формата, точность и смысл цитат до использования признаков.
При отсутствии/устаревании/невалидности артефакта используется baseline,
причина попадает в diagnostics.warnings. Отсутствие AI-ключа не блокирует запрос.
Исходный CSV остаётся единственным источником жёстких условий. Признак, который
противоречит структурированным полям, отбрасывается с предупреждением.

## Проверка данных и примеры

Загрузчик использует стандартный csv.DictReader с encoding="utf-8-sig" и newline="".
categories/event_formats/languages/busy_dates разделяются `|`; флаги только
строки `True`/`False` (прочее — ошибка); price_from_kzt — int;
max_hours — число либо None при пустой ячейке; id — строка; description дословно.
В ошибке записи line — последняя физическая строка CSV-записи (описание может быть многострочным).

Загрузчик проверяет все строки, обязательные поля, строгие типы, уникальность id,
календарь, положительные числа, словари городов/категорий/языков/форматов, флаги.
Словарь категорий взят из HTML-превью; незнакомые значения требуют явной проверки,
а не молчаливого исправления. Пустой файл или плохая строка блокируют весь каталог.
Отчёт CLI показывает число записей, фактические значения с частотами, флаги,
пустые описания, несколько категорий и null max_hours. Число ≠66 — предупреждение (тестовые каталоги
допустимы), дубликаты/невалидные поля — ошибка с номером строки/id.

`docs/examples/responses.json` содержит явно учебные примеры всех трёх исходов.
Они не подключены к runtime. Реальные сценарии отдельно проверены в
`tests/test_real_demos.py` и `docs/demo.md` независимым алгоритмом, не заглушкой API.
